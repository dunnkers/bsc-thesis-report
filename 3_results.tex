\section{Results}\label{sec:results}
In the results, first the performance of the fusion algorithm is explored using a 2-element feature vector. Next, the 5-element feature vector fusion algorithm performance is analyzed and compared to the 2-element feature vector. Then, an analysis is made on the difference in performance between the supervised, unsupervised and fusion approach. Lastly, pipeline performance measurements are taken into consideration.

\subsection{Fusion algorithm using a 2-element feature vector}
The data-set was tested under several configuration conditions. Different- pixels size configurations and classifiers were used, all using a $10$-fold cross validation setup. The study focused on two classifiers: a \textit{Support Vector Machine} using LibSVM \citep{chang2011libsvm} and \textit{Gradient Boosting} using XGBoost \citep{chen2016xgboost}. General results of the prediction are first explored, using the \textit{XGBoost} classifier. Afterward, a comparison between the two classifiers is made.

Important to note is the fact that for the $525$x$1050$ cache, results are only obtained for XGBoost. This is due to the very high testing times of the SVM classifier when large pixel size configurations come into play. Although training times for both classifiers remain somewhat constant despite increasing pixel sizes, testing times per image get significantly higher with higher pixel size configurations. The reason for this is that the training set is sampled, reducing the number of pixels that are used for training, which applies to all pixel configurations. A max amount of samples of $max\_samples$ are taken per image. In testing, however, an increase in pixel size means a significant increase in total data-points that have to be predicted. \subsection{Pipeline performance}\label{sec:pipeline-performance}
% Pipeline is optimized..
Pipeline performance is an important aspect in the perspective of scalability. The pipeline was optimized by enabling parallel-computing computations as much as possible. This includes caching multiple images simultaneously, training using a \textit{BaggingClassifier} and thus enabling using multiple cores using $n\_jobs=-1$ and enabling parallel estimation again by setting $n\_jobs=-1$ on classifier instances. The pipeline performance was measured for the case where a 2-element feature vector was constructed.

% Cache is kinda fast already, not an integral part.
The cache pipeline step executes at a reasonable speed, and at foremost- is a one-time process. Once images have been cached, different training- and testing configurations can be used without re-generating the cache. For this reason, only the transformation, training and testing pipeline steps were bench-marked, since they form the most integral part to the pipeline's performance. See Figure~\ref{fig:pipeline-performance}.

\begin{figure}[ht]
  \centering
  \includesvg[width=\linewidth]{img/max_samples=200,folds=10-pipeline-performance.svg}
  \caption{Pipeline performance using an Intel Core i7-3820 Quad CPU @ 3.60GHz, running 64-bit Ubuntu 19.04 system at 8,0 GiB RAM.
  }\label{fig:pipeline-performance}
\end{figure}

% Talk about how transformations get slower with increasing pixel sizes.
Visible in the figure (Figure~\ref{fig:pipeline-performance}), is that transformation performance decreases in somewhat linear fashion. This is because of the fact that image width and height in increasingly large pixel size configurations are not doubled, but increased by smaller increments. Transformation performance is very fast up to the $175$x$350$ cache level. After this, performance slows down fast.

% Talk about how training times remain somewhat constant.
Training times, however, remain rather constant across the entire cache range. This is because classifiers train upon a sampled data-set, for which the sample size remains constant across all caches. It is visible though, that \textit{SVM} takes longer to train than \textit{XGBoost}.

% Talk about how test times are through-the-roof when pixel size configurations increase.
Test times, however, are significantly impacted by pixel size configurations; for every increase in pixel size configuration, a significantly higher amount of pixel-values have to be predicted. Because of the great differences in test times, the pipeline test performance chart was depicted in a \textit{logarithmic} scale. For the $525$x$1050$ pixel size configuration, a \textit{SVM} takes at least $158$ seconds to predict $1$ image, whilst \textit{XGBoost} takes $3$ seconds for the same case.
